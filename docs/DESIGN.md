# 设计说明

## 起点：三次「机器变慢但什么都没报错」

2026-11 一次真实排查，同一台机器上三种不同形态的浪费同时存在：

| 现象 | 真实数据 | 为什么没被发现 |
|---|---|---|
| 4 个孤儿 headless Chrome | 各占 2.5–3.6 核，合计约 12/20 核 | 启动脚本抛错时跳过了 `chrome.kill()`，父进程被 systemd 收养；页面静止也照吃 CPU |
| GNOME 索引器 | 13 天读了 854 TB、209 亿次 read 系统调用 | `$HOME` 被递归索引，node_modules 和构建产物全进库；服务状态一直显示 `active` |
| quickshell | 50,654 个 Wayland keymap fd，占 soft limit 77% | fd 泄漏不报错，只是「再过一阵就会开始莫名失败」 |

共同结构：**持续性的资源浪费 + 零错误信号 + 无人盯屏**。这不是「监控不够灵敏」，
而是「没人会去看的那类指标」。于是设计目标不是「采集更多」，而是：

> 把「谁也不看的浪费」变成「一眼就知道该不该管、该谁管」的一屏。

## 模型：采样 → 规则 → 动作 → 看板

```
tick (10min)                                        board (always on)
  ├─ sampler    /proc 差值采样           ──────┐
  ├─ rules      7 条持续型判定                    │
  ├─ remediate  6 道护栏后处置                    ├──▶  SQLite: ticks / incidents / actions
  └─ notify     严重且未认领才升级                │        │
                                                 └────────┴──▶  看板 + 认领 → 停止升级
```

四个角色的职责边界刻意不混：

- **sampler 只回答「现在是什么样」**。不判定、不记录策略，产出可测试的纯数据。
- **rules 只回答「这算不算持续异常」**。除阈值外不关心副作用，也不调用系统命令。
- **remediate 是唯一能动系统的地方**，因此它自己复核全部前置条件，不信任检出阶段。
- **board 只读数据库**，不采样、不判定，所以它挂掉不影响巡检，反之亦然。

## 为什么用差值而不是 `ps` 的平均值

`ps -o %CPU` 是「进程生命周期内的平均占用」。一个跑了 12 小时、稳定吃 15 核的进程
和刚启动的进程在它眼里毫无区别；反过来一个跑了三天大部分时间空闲、刚烧起来的进程
会被严重稀释。`agent-guard` 每次采样记录每个 pid 的 `utime + stime`，两次之差除以真实
间隔得到瞬时占用。副作用是：首次采样没有基线，CPU 规则要等第二个 tick 才有意义——
这是诚实的代价，不伪造数据。

## 为什么「持续」是核心参数

单点尖峰几乎总是正常行为：编译器、压缩、构建、批量转码都会瞬间吃满所有核。把它们
报出来，等于训练用户忽略告警。因此每条规则都有 `ticks`（连续采样次数），默认：

- CPU / 负载 / 内存：2 次（20 分钟）——真事故不会 20 分钟就结束
- IO / fd / 压力：1 次——这类是「已经出不来了」而不是「正在忙」
- 孤儿浏览器：1 次——它按定义就是垃圾，无需等

## fd 规则为什么要按继承链聚合

`fork` 会复制父进程的整个 fd 表。一个泄漏在 `quickshell` 里的 bug，会让 `wl-paste`、
`inotifywait`、每个 python 助手进程都「持有五万个 fd」。逐进程报告的结果是十条同源
告警，用户会关掉告警。实现上沿 `ppid` 上溯到「最大的那批 fd 表」的根部，只报一次，
并附上「还有 N 个进程在共享这张表」，同时给出链条里最紧的那个 soft limit 占用率。

## 自动处置：为什么只做一类，为什么有六道护栏

可供自动处置的选项很多（重启服务、清缓存、杀进程），但**只有一类在语义上永远安全**：
驱动进程已死、无人连接的自动化浏览器。其余都需要判断「这东西是不是有用」。

护栏的写法来自一次事故：早期版本用「命令行含 `--headless` + 父进程已死」判定，
把一个用户级守护进程（`ducter up --headless --port 7777`）当成孤儿浏览器杀了。
修正后的规则是**双条件**：comm 必须在浏览器白名单里，**且**命令行必须带自动化特征
（profile 目录或调试端口）。守护进程第一关就出局；人自己开的 Chrome 第二关出局。

另外几条护栏各自的理由：

| 护栏 | 防的是什么 |
|---|---|
| uid 一致 | 跨用户误杀，权限最高的那类错误 |
| 无调试客户端 | 杀掉一个 agent 正在用的浏览器，等于破坏它的上下文 |
| 不是 `.service` 的 MainPID | systemd 管理的服务由 systemd 决定生死；`.scope` 不算（它只是分组） |
| 父进程仍未回到 | 采样与处置之间存在时间窗 |
| 单 tick 上限 | 一次配置失误不至于清空整台机器 |

每次拒绝都记为 `skip` 动作，带理由。**「没杀」和「为什么没杀」一样重要** ——
否则用户会以为护栏没生效。

## 告警路由：看板免费，聊天收费

聊天渠道的边际成本是注意力，而不是带宽。设计上：

1. **看板承载全部信息**：当前状态、告警卡片、动作流水、历史时间线。
2. **聊天只承载决策**：`severity ∈ escalate_severities` **且**持续超过
   `escalate_after_unacked_seconds` **且**未认领，才升级一次，且受冷却约束。
3. **认领即静音**：在页面上点一下，后续不再升级，也不影响告警本身在时间线上的记录。

这条策略就是为了修掉「群里全是告警，于是所有人都静音」的死循环。

## 数据模型

```sql
ticks    (ts, load1, cores, mem_*, pressure, top_json)   -- 趋势线与「当时谁在吃」
incidents(key, kind, severity, title, body, first_seen, last_seen,
          closed_at, acked_at, escalated_at)             -- 一条告警的完整一生
actions  (ts, kind, target, detail, ok)                  -- 系统上真正发生过的事
```

`incidents.key` 稳定标识同一问题（例如 `cpu:hog:chrome:1140288`、`fd:1517285`），
消失后 `closed_at` 打点而不是删除，所以「这个问题今天出现几次、持续多久」是可查的。

## 已知限制

- **非 Linux 主机**只能拿到进程名与 CPU，fd / IO / PSI 规则自动跳过，不假装有数据。
- **首次采样没有 CPU 基线**，第一个 tick 的 CPU 规则必然沉默。
- **cgroup 归因粗糙**：孤儿进程被 systemd 收养后归属会话 scope，目前只能按进程定位，
  无法说「这属于某个 agent 会话的开销」。这是路线图里的下一项。
- **remediate 只处理浏览器**。索引器、编译器、守护进程的异常只报警不动手，因为判断
  它们是否还有用需要人的上下文。

## 为什么不内置 Web 框架

看板是单个 `index.html`（原生 JS + 一个 SVG 折线图），服务端是 `http.server`。
理由是这类工具的部署成本决定它会不会被真的装上：能 `git clone` 就跑到一台没网、
没 node_modules、没构建工具的老服务器上，比好看重要。前端只做三件事：轮询、渲染、
发一个 `POST /ack`。
